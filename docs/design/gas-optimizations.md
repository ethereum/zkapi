# Gas optimizations: designs and trade-offs

This document describes zkAPI's gas work, one design per section: what
changed, how it works, what it costs, and what it gives up. The work lands as
three stacked pull requests:

| Pull request | Branch | Implements |
|---|---|---|
| Base | `pr/gas-base` | §1 folded verifier, §2 verify-once gasless exits and the escape lock, §3 exit storage compaction, §4 fast Poseidon |
| Design C | `pr/leaf-bound`, on the base | §5 leaf-bound exits |
| Batched exits | `pr/batch-exits`, on the base | §6 batch verifier, exit batcher, challenger batching, close relay, transit-account reuse |

The design C and batched-exit pull requests each build on the base alone and
do not depend on each other; this document, added by the base, describes all
three. All figures are gas measured as separate, cold transactions under
mainnet (Prague) pricing unless stated otherwise, with `GasBaseline.t.sol`, the
pinned snapshots and the acceptance harness. The "After" column, and the
per-exit figures of §5 and §6, are measured on the version with all three
merged; a section gives the figure of its pull request alone where it differs.

## 0. Where the gas went

- A deposit cost ~970k gas: about 89% of its execution gas was 35 Poseidon permutations at ~23.4k each. 32 of them updated the depth-32 note tree on every deposit; 3 hashed the leaf. The tree frontier wrote only one storage slot, so storage was not the main cost.
- An exit cost ~300–500k: the Groth16 verification (~277k, of which ~25k was Solidity overhead around the precompiles), plus new storage slots (a pending escape wrote 7).
- Sepolia already prices state creation as EIP-8037 does: a new storage slot costs ~110k gas instead of 22.1k. That is why the Sepolia deposit used 1,256,649 gas against ~970k for the same bytecode under mainnet rules. Every design below is also judged by how many new slots it writes.

## 1. Verifier: folded constants and straight-line assembly

*Base pull request.*

**What.** The Groth16 adapter generated by `compact.rs` is straight-line assembly instead of struct-based Solidity, and it folds the public inputs that are fixed per deployment into the first verification-key point.

**How.**
- Seven withdrawal inputs (protocol version, chain ID, vault address, the four signing-key coordinates) and five request inputs never change for a deployment, and the vault already requires them to equal its own constants.
- The adapter's constructor takes `(vault, stateKeyX, stateKeyY, clearanceKeyX, clearanceKeyY)` and computes `IC0' = IC0 + Σ cᵢ·ICᵢ` once, through the same precompile routine that range-checks the constants. These values are public immutables.
- A statement takes the fast path only when every folded word equals its immutable. Any other statement (another fork, vault or key) is verified over all inputs, more slowly but correctly.
- The assembly reads inputs from calldata, accumulates the multi-scalar sum in place, builds the 24-word pairing input in place, and keeps every check of the old verifier: every input < r, every proof word < q, narrow-field cleanliness exactly as the ABI decoder checks it, proof length 256, and the 0/1/2 scalar shortcuts.
- `Deploy.s.sol` predicts the vault address, then asserts the adapter's folded vault, chain and keys against the deployed vault before writing any manifest.

**Gain.** Withdrawal verification 276,950 → ~217,000 (11 → 5 scalar multiplications, overhead 25k → 4k); request verification 274,774 → ~228,500.

**Trade-offs.**
- The adapter is deployment-specific: its codehash depends on its immutables, which `expected-codehashes.mjs` fills in.
- A wrong vault-address prediction or a chain fork does not break verification. It costs ~40k more per proof, which the deploy script's assertions prevent.

## 2. Gasless exits: verify once, transient records, escape lock

*Base pull request, including the escape lock: it fixes a bug that predates this work.*

**What.** A sponsored (ERC-4337) close or escape used to verify its proof twice: once in the paymaster's validation and again in the vault. Now it is verified once.

**How.**
- `verifyWithdrawalOnce` always verifies in full, then writes a transient (EIP-1153) record at `keccak256(destination ‖ keccak256(inputs ‖ proof))`.
- The vault's ordinary `assertValidWithdrawal` returns early only if that exact record exists. Transient storage is cleared at the end of the transaction and rolled back on revert.
- The destination prefix makes the slot storage associated with the sender under ERC-7562 (STO-021; STO-022 when the operation deploys the transit account, so the factory's stake is load-bearing).
- The paymaster's `received`/`receivedGas` bookkeeping, previously two new slots written and deleted in the same transaction, is transient.
- A transient per-transit-account escape lock fixes a bug present before this work: two sponsored escapes from one transit account in one bundle were both accepted, and the first escape's forward evidence was lost, at the operator float's expense.
- Paymaster gas constants are re-derived by the rules in `test/gasless/Gas.t.sol`.

**Gain.** About −250k `actualGasUsed` per sponsored close or escape.

**Trade-offs.**
- The vault now trusts the adapter's record code as well as its verifier.
- The paymaster's constants are measured under mainnet pricing. Its constructor refuses chains that price a new slot above 25,000 gas, and `checkGasSchedule()` lets anyone retire sponsorship permanently once a fork reprices state creation. **Gasless exits are therefore off on Sepolia today and will retire at mainnet's EIP-8037 fork**, until a paymaster v2 with per-chain constants is deployed.
- The paymaster is 23,950 bytes, 626 below the EIP-170 limit (23,848 and 728 with design C).

## 3. Exit storage compaction

*Base pull request.*

**What.** `usedNullifiers` and `challengedNullifiers` are one word per nullifier (bit 0 used, bit 1 challenged), and a pending escape is stored in fewer slots.

**How.**
- The getters keep their selectors and return values, and every check keeps its order.
- An escape record is the nullifier N, then one packed slot holding the deadline, final balance, conceded amount and deposit amount, with explicit bounds before every narrowing cast.
- N's nullifier word carries the successor nullifier N+1, and N+1's word carries the destination.
- The proof's `activeRoot`, which the vault never read, is no longer stored.

**Gain.** An escape writes 4 new slots instead of 7 (−71k on mainnet, about −335k under EIP-8037 pricing); a defeat writes none instead of one.

**Trade-off.** `pendingWithdrawals` word 1 (`activeRoot`) is always 0.

## 4. Fast Poseidon, proven in Lean

*Base pull request.*

**What.** The on-chain Poseidon is a generated, assembly-only runtime contract instead of a via-IR Solidity library.

**How.**
- `zkapi-proof`'s `poseidon_runtime.rs` generates `Bn254PoseidonRuntime.sol`. It is a single inline-assembly block compiled with solc's legacy pipeline:
  - a fully unrolled permutation in scaled sparse form (7 `mulmod` per partial round);
  - constants as literals;
  - lazy modular reduction: `add` instead of `addmod` wherever the operand bounds provably total at most 5p < 2^256.
- It exposes the old library's selectors and ABI checks: `compress`, `hash5`, `insertPath32`, `compressPairPath32`.
- The vault receives the runtime's address as a constructor argument, checks it at construction, and calls it with `STATICCALL`, so the hasher can never write vault state.
- The old library stays as a test-only differential oracle.

**Proof** (`protocol/formal`, Lean 4 + Mathlib). Every theorem uses only the standard axioms: no `sorry`, no `native_decide`, and an axiom audit over the whole namespace.
- The scaled schedule equals the reference Poseidon permutation for every state, including a domain constant in the capacity lane. `compress`, `hash5` and the sponge equal zkAPI's reference definitions.
- Every lazy addition stays below 2^256 for all inputs, including words ≥ p, and the outputs are the canonical field values.
- A Yul parser and scoped semantics in Lean read the token stream of the production source. For all calldata shorter than 2^48 bytes, the assembly block returns the correct `compress`, `hash5`, `insertPath32` and `compressPairPath32` results, and reverts exactly where the old library's ABI decoder did.
- The proof is tied to the code by data, not by hand:
  - 30+ known-answer vectors from the Rust and Solidity tests and all 33 zero hashes are checked;
  - the generator's output is checked byte for byte against the proof data;
  - CI runs the checks and builds the project.

**Gain.** One permutation 23,432 → 12,728 gas; deposit 970,789 → 573,516 before design C.

**Trade-offs.**
- solc's Yul-to-bytecode step and the few lines of Solidity around the block are trusted, not proven.
- Neither the old library nor this runtime has had an independent audit. No Poseidon contract for Ethereum that we could find has a public dedicated audit: `poseidon-solidity`, used by Privacy Pools and Semaphore v4, states that it is unaudited.
- For comparison: `poseidon-solidity` costs 21.1k per hash, and Railgun pays ~44k per hash in `insertLeaves`.
- The vault constructor gained an argument.

## 5. Design C: leaf-bound exits

*Design C pull request.*

**Idea.** Today every deposit recomputes and stores a Merkle root because withdrawals prove "my leaf is in the tree", although a withdrawal already reveals which note it is. In C the vault stores each note's leaf, and a withdrawal proves "I know the secret behind the leaf you stored for note n". The tree remains only for anonymous requests, which are the part that needs anonymity, and its root is computed from on-chain state by a free view.

**Circuit** (`zkapi-v2-concession-v2`, vault revision 4).
- **Leaf.** One Poseidon permutation instead of the three-permutation sponge:
  `leaf = compress("zkapi.v2c.leaf", H_reg(s, 0), noteId·2^192 + amount·2^64 + expiry)`.
  The packing is injective because the circuit already range-checks the fields as UInt32, UInt128 and UInt64.
- **Withdrawal statement.** It no longer contains Merkle membership.
  - Public input 3 is the note leaf and public input 8 is `noteFields`; the other 14 inputs are unchanged.
  - The circuit enforces `noteFields` = the packed fields, `leaf = compress(DOMAIN_LEAF, H_reg(s,0), noteFields)`, and nullifiers derived from the same `s` and `noteId`. All balance rules are unchanged.
  - Constraints drop from 28,772 to 20,545, proving from ~373 ms to ~279 ms, and the proving key from 5.58 MB to 4.26 MB.
- **Request statement.** Unchanged apart from the leaf: the same public inputs, and the same 32-level membership proof over every note (23,990 → 23,507 constraints).
- The development keys were regenerated once. The ceremony has not run.

**Vault.**
- `deposit` computes the leaf and stores `leaf | status << 254` in one word (`noteRecord(noteId)`), then updates only the tree frontier.
  - The frontier update costs `trailing_ones(noteId)` compressions: 1 on average, 0 for every even note ID.
  - It no longer computes or stores a root, and `knownRoots`/`isKnownRoot` are gone.
  - A `minDeposit` immutable (deploy default 0.001 ETH) makes anonymity-set spam lock up capital.
- `mutualClose` and `initiateEscapeWithdrawal` require `proof.leaf == noteRecord(noteId).leaf` and status Active, then verify the proof.
  - The deposit amount and expiry come from the proof-bound `noteFields`, with `amount ≤ MAX_NATIVE_UNITS` and checked narrowing.
  - Exiting needs only the user's secret and the vault's own record: no Merkle path, root, indexer or event logs.
- `currentRoot()` (same selector) is a view computing the request root from the stored frontier, about 0.5M gas in `eth_call`.
- `noteLeaves(start, count)` and `frontier()` let anyone rebuild the request tree from state at a pinned block, without event logs.
- `recordRoot()` is an optional, permissionless audit trail: it stores `root → (noteCount, blockNumber)` and emits `RootRecorded`. It costs ~465–543k, paid by its caller; nothing in exits, requests or clearance depends on it.
- `retireClosedLeaf` keeps its ABI but verifies only the sub-path below level ℓ = msb(noteId XOR nextNoteId).
- `claimExpired` and `effectiveExpiry` take the leaf preimage (commitment, amount, expiry), since storage holds only the leaf.

**Off-chain.**
- **Request roots (server):** the server accepts any request root it has itself read from the vault in the last `request_root_grace_seconds` (default 60), because cheap deposits change the root often.
  - Only vault-read roots enter the window, and the tree only grows, so an older root contains only real notes.
  - Closed notes are still refused through their spent nullifiers.
- **Clearance:** reads `noteRecord` fresh every time.
- **Indexer:** can bootstrap from state.
- **Clients** (Rust, Go, SDK, companion): exit from the leaf and rebuild request paths from pinned vault state.
- **Deposits while the indexer is down:** a second source must agree before a deposit activates.

**Gain.**

| | Before C | C, mainnet | C, EIP-8037 pricing |
|---|---|---|---|
| Deposit, average | 579,889 | 87,633 | ~176k |
| Deposit, even note ID / note 1023 | 573,516 / 609,678 | 68,327 / 243,986 | — |
| New slots per deposit | 3 (4 after any pause) | 1 | 1 |
| Retire a closed leaf | 939,846 | 37,678 – 471,788 | — |

**Trade-offs.**
- **Circuit and client migration.** It must ship before the ceremony; after it, C would require a new ceremony.
- **Single-transaction drain (layout C1, chosen by the owner).** The deposit amount used for payouts comes from the proof, not from storage. With a sound verifier and setup this is exactly as safe as before, because the amount is bound into the leaf. If the verifier or the trusted setup were broken, one forged exit could claim the whole vault instead of one note's deposit. The two-slot layout C2 would keep a storage cap per note for +22.1k per deposit (+~110k under EIP-8037).
- **Request root window.** The server accepts roots up to 60 s old instead of exactly the current one. Clients should always use the latest root to avoid standing out.
- **`claimExpired`** costs ~12k more (operator-paid).
- **`currentRoot()` cost.** It needs an RPC that allows ~0.6M gas per `eth_call` and block-hash-pinned reads.
- **Root history.** Historical roots are not stored unless someone calls `recordRoot()`. Nothing in the protocol needs them.
- **Anonymity set.** It is unchanged: every deposit is in the request tree. Cheap deposits make dummy notes cheaper, which `minDeposit` counters.

**Rejected alternative: design B (lazy root).** Deposits update only the frontier, and a permissionless `recordRoot()` records roots that exits must cite. It needs no circuit change, but exits keep depending on a recorded root. Either an operator-run keeper pays for recording, or the exiting user pays ~0.5M. It was dropped in favour of C, which removes the dependency.

## 6. Batched exits (adapted from Kohaku)

*Batched-exits pull request.*

**Origin.** Kohaku's paymaster flows (Privacy Pools and Tornado in `ethereum/kohaku`, contracts in `Robert-MacWha/privacy-paymaster`) consolidate several notes into one ERC-4337 operation. They save the per-operation overhead, but still verify each proof separately. Their pattern of executing the withdrawal inside paymaster validation writes protocol storage during validation, which ERC-7562 forbids. zkAPI keeps its compliant verify-once path instead and adds cryptographic batching, which Kohaku does not do.

**Batch verifier** (generated into the adapter by `compact.rs`; reference implementation in `zkapi-proof/src/batch.rs`).
- `verifyWithdrawalBatch`, `verifyRequestBatch`, and their `…Once` variants, which write the same per-item records as verify-once (requests under a separate `REQUEST_RECORD` namespace > 2^160).
- **Check.** A random-linear-combination check with one multi-pairing of n + 3 pairs: `∏ e(−rᵢAᵢ, Bᵢ) · e((Σrᵢ)α, β) · e(Σ rᵢLᵢ, γ) · e(Σ rᵢCᵢ, δ) = 1`.
  - r₀ = 1, and rᵢ is a 128-bit Fiat–Shamir challenge from a keccak seed over a domain tag, the verifying-key hash, n and every byte the verifier reads.
  - The input multi-scalar sum is shared across proofs, with the folded constants and a per-item generic fallback.
  - Every range, point and narrow-field check of the single verifier is kept. The verifier is all-or-nothing.
- **Gain.** Each extra proof costs ~50k instead of ~220k: 16 withdrawal proofs cost 998,220 against 3,609,818 one by one.

**ExitBatcher** (`src/periphery/ZkApiExitBatcher.sol`, permissionless, stateless, deployed with every vault).
- Entry points: `mutualCloseBatch`, `initiateEscapeBatch`, `challengeBatch` (defeats and raises), `finalizeBatch`.
- **Flow.**
  - It batch-verifies every proof first, then makes one ordinary vault call per item under a per-kind gas cap. Each call hits the recorded proof (~1.4–2.5k gas).
  - An item whose state changed in the meantime (front-run, already closed, under design C `NoteLeafMismatch`, …) is skipped with an event, not reverted.
  - Proof validity does not depend on state, so skipping cannot be abused to apply an unverified item.
  - The batcher reserves each item's worst-case gas up front, reverts `BatchOutOfGas` if starved, and holds no ETH.
  - Payouts are bound by each proof, so a batcher cannot redirect funds.
- **Item gas caps** are chosen per chain at deployment by measuring a new storage slot:

  | Kind | Mainnet | EIP-8037 |
  |---|---|---|
  | close | 250k | 500k |
  | escape | 250k | 600k |
  | defeat | 150k | 150k |
  | raise | 150k | 150k |
  | finalize | 300k | 400k |

- Gas per exit with all three pull requests merged (leaf-bound statements):

  | Kind | Single | n = 2 | n = 4 | n = 8 | n = 16 |
  |---|---|---|---|---|---|
  | close | 309,736 | 230,105 | 172,438 | 143,622 | 129,226 |
  | escape | 369,810 | 283,007 | 225,867 | 197,307 | 183,044 |
  | defeat | 284,904 | 197,363 | 139,752 | 110,965 | 96,575 |
  | raise | 278,042 | 192,481 | 135,853 | 107,562 | 93,430 |
  | finalize | 56,681 | 37,583 | 32,572 | 30,067 | 28,815 |

  With the batched-exits pull request alone (revision-3 statements, without design C), per exit at n = 16: close 129,395 against 307,710 single, escape 183,214 against 367,185, defeat 96,766 against 286,960, raise 92,933 against 277,479, finalize 28,760 against 45,063.

  A batch of one costs ~15k more than the direct call, so relayers send lone items directly.

**Operator flows.**
- **Challenger batching** (`zkapi-serverd` challenge service). Defeats and raises are flushed in batches with deadline awareness:
  - the gas limit is the verification bound plus n × item cap;
  - the exact batch is simulated with `eth_call` and bisected on failure;
  - single calls are used near deadlines.

  This makes the operator's defence about 3× cheaper than the escapes it answers.
- **Close relay** (`POST /v2/withdraw/relay`, `/relay/terms`, `/relay/fee`). It is opt-in for clients (`--fees relay`, `fees: 'relay'`).
  - The relay fee is charged as one metered request before the clearance, so it sits inside the treasury share with no circuit change.
  - Batches flush at 16 items, at a configured age, or when an item nears `validUntil`.
  - Clients self-submit at `validUntil` − 20 minutes if the batch has not landed. The relay runs under its own signer key and role.
- **Transit-account reuse.** Gasless exits reuse one transit account per payout address: the owner key is derived per payee with HKDF from the wallet seed. A later sponsored close to the same payee is ~115k cheaper (600,219 → 485,843 in the acceptance run).
  - This links one wallet's exits to the same payout address. That address is already public.
  - `--fresh-transit` or `config --transit-accounts fresh` opts out.

**Trade-offs.**
- Batching saves gas only when someone collects exits and waits to fill a batch. Users can always submit alone.
- The batch verifier adds ~6.7 KB of assembly to the code the vault trusts (adapter 19,858 bytes with design C, 19,885 without). A bug in it or in the records could let notes be drained, so it needs an audit together with the single verifier.
- Single defeats and raises cost ~600 gas more (the request-record check), and every single exit ~170 more (a larger dispatcher).
- Inside ERC-4337 validation, ERC-7562's 500k validation limit allows only ~2 exits per operation. Batching therefore targets direct and relayed transactions, not the gasless path.

## 7. Not done, and required before mainnet

- **Trusted-setup ceremony:** run it on the `zkapi-v2-concession-v2` R1CS, starting with the rehearsal.
- **Paymaster v2:** per-chain gas constants measured under EIP-8037 pricing, before mainnet adopts it. Optional extras: EIP-7702 senders for closes, several exits per operation. The current paymaster has 626 bytes of headroom (728 with design C).
- **External audit** of the vault, the Groth16 adapter including its batch section and records, the ExitBatcher, the paymaster, and the Poseidon runtime. The Lean proof covers the runtime's correctness, not its specification or trust assumptions.
- **Unmeasured cases:** the gas figures under EIP-8037 pricing that are marked approximate (~) are estimates from the measured cost of a new slot, not end-to-end measurements.
