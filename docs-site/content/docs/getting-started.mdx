The repository contains the browser SDK, Rust runtime and proof libraries,
and Solidity native ETH vault. Use Rust, Node.js 24 or later, and Foundry for
local development.

## Build and test

From the repository root:

```bash
cargo build --release --workspace --locked
cargo test --release --workspace --locked
cargo test --release --manifest-path protocol/rust/Cargo.toml --workspace --locked
npm ci
npm run test:sdk
npm run verify:assets
npm run verify:builds
```

Run `forge test` from `protocol/contracts/` for vault and verifier tests.
`npm run verify:builds` checks that a `not_deployed` placeholder profile
refuses to build and that a deployed one builds; `npm run build:browser` and
`npm run build:mainnet` refuse the packaged placeholders until a revision-3
vault is deployed and pinned.
Committed proof assets are already included; consuming the SDK does not
require generating new setup keys. The protocol source and Solidity
dependencies are tracked under `protocol/`; no submodule initialization is
required.

To generate request and escape-withdrawal proofs with the packaged browser
WASM and proving keys, then verify them with the native verifier:

```bash
cargo run --release --locked --manifest-path protocol/rust/Cargo.toml \
  -p zkapi-proof --example wasm_roundtrip -- \
  "$PWD/scripts/prove-browser-fixture.mjs" "$PWD/sdk"
```

## Browser integration

Install the SDK from a reviewed immutable repository revision or its `npm pack`
tarball. Configure it before initializing the wallet:

```js
import { configureBrowserSdk } from '@openanonymity/zkapi-browser-sdk';
import client from '@openanonymity/zkapi-browser-sdk/client';

configureBrowserSdk({
  configUrl: '/zkapi/v2c/browser-config.json',
  workerUrl: '/zkapi/v2c/assets/zkapiWasmWorker.js',
});

await client.init();
const unsubscribe = client.subscribe(snapshot => renderBalance(snapshot));
```

The host supplies the payment UI and an EIP-1193 wallet provider. The SDK owns
private note state, proof generation, transaction journals, receipt recovery,
and settlement. Build the static worker, WASM, keys, and configuration with
`buildBrowserSdkAssets` from the package's `/build` export.

Use the repository's `sdk/README.md` for the complete integration contract,
including external wallet providers, durable manual signing, recovery, the
exit rules, the exit kit and the user's exit RPC. The trusted configuration
pins the network, native vault, contract code hashes, server signing keys,
proof asset hashes, and deployment manifest. Protocol amounts are whole gwei.
Until a revision-3 vault is deployed on a network, its packaged profile is a
placeholder and the build refuses it (`deployment_not_deployed`). During the
migration a host serves this build at `/zkapi/v2c/` beside the legacy build;
see `examples/sample-host`.

## Runtime services

The root workspace builds the server and indexer runtime libraries,
`zkapi-indexerd`, `zkapi-challenged`, and the `zkapi` operator CLI. Start the
indexer, then create the database with `zkapi db init`, then start the
challenger and finally `zkapi serverd`; use `--help` for current
configuration flags. The server and browser must use the same deployment,
keys, setup and `zkapi-v2-concession-v1` circuit.

`ZKAPI_STATE_SEED` and `ZKAPI_CLEAR_SEED` are required, with no defaults, even
on a local chain. Generate each one independently, for example with
`printf '0x%s\n' "$(openssl rand -hex 31)"`. `zkapi signing-keys` derives the
public keys to pass to the vault constructor; it and the server refuse zero
or guessable seeds, one key for both roles, and the published development
keys in either role. `zkapi serverd` then refuses to start unless its native
billing RPC serves `--chain-id` and the derived keys equal the vault's
immutable keys. See the
[deployment](https://github.com/ethereum/zkapi/blob/main/docs/deployment.md),
[challenge service](https://github.com/ethereum/zkapi/blob/main/docs/challenge-service.md)
and [concession-vault migration](https://github.com/ethereum/zkapi/blob/main/docs/migration-concession-vault.md)
guides for operation.

## Select the matching setup

Three setup directories are checked in:

- `protocol/setup/v2-concession`: the production setup `mpc-1` of circuit
  `zkapi-v2-concession-v1`, from a multi-party ceremony. It holds no keys
  until that ceremony has run, and release builds load no other keys.
- `protocol/setup/v2-concession-dev`: the development setup `dev`, generated
  by one party, for tests, CI, the Sepolia drill vault and any vault
  deliberately deployed on it with `ALLOW_DEV_SETUP=1`. Only builds with the
  `dev-setup` feature load it.
- `protocol/setup/v2`: the keys of the legacy circuit `zkapi-v2-note-bound-v1`,
  for the release line `release/v2-note-bound`.

Keep the proving keys, verifying keys, Solidity adapter, and browser WASM from
the same release and setup together. Check `proof_setup.circuit_id`, the setup
ID, key and WASM hashes, chain ID, vault address, contract code hashes and
state/clearance signing keys against independently trusted deployment values.
Each key file's header names its circuit, setup and kind and catches
accidental mismatches; it does not prove setup provenance or replace hash
pinning.

Only when intentionally creating a **new** development deployment, generate a
separate setup directory:

```bash
./target/release/zkapi setup --output-dir protocol/setup/new-deployment
```

This creates new incompatible development keys and a matching verifier, which
release builds refuse. Production keys come only from the ceremony described
in `protocol/setup/v2-concession/README.md`, and production use also requires
the independent review of the design and setup.

The vault's verifier and signing keys are immutable. The server, frontend and
manifest must match those deployed values before a wallet is funded.
