```text
Browser SDK -> WASM prover -> server -> usage settlement and signed next state
     |                         |
     v                         v
  indexer                 SQLite transcripts
     |
     v
Native ETH vault <-------- challenge service
```

`protocol/rust/crates/zkapi-types/src/wire.rs` defines the protocol's JSON
messages. Runtime handlers in `crates/zkapi-serverd/src/routes.rs` and
`crates/zkapi-indexerd/src/http.rs` define the supported routes. The challenge
service reads the server's append-only request evidence and the vault's
pending escapes, and submits defeats, raises and leaf retirements through a
restricted signer.

## Proof and field encoding

The active circuit is `zkapi-v2-concession-v1`. Requests keep the v2 JSON
shapes and public-input order; withdrawals and clearances use the 16-input
`WithdrawalPublicInputsV2C`. The proving/verifying keys and the vault's Groth16
adapter must match that circuit and setup. Pin the circuit ID, setup ID,
artifact hashes, vault address, contract code hashes and server signing keys
for the configured deployment.

Field values use `0x`-prefixed hexadecimal strings. The Rust type
`Felt252` carries BN254 scalar-field values; it does not select the
Stark field. Curve points use `{ x, y }` and Schnorr signatures use
`{ r_x, r_y, s }`.

An HTTP proof is `{ backend: "groth16_bn254", proof: base64 }`. Decoding
`proof` yields exactly 256 bytes: eight canonical, 32-byte big-endian BN254
base-field coordinates in the order `A.x, A.y, B.x.c0, B.x.c1, B.y.c0,
B.y.c1, C.x, C.y`. These same bytes are passed to the vault's proof adapter.
Public inputs are supplied separately and verified directly. The v2 proof
object has no `public_output_hash` or private witness envelope.
