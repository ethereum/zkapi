---
title: ZkApiVault
description: Native ETH settlement with note-bound Groth16 verification and the concession exit
---

The wallet calls `ZkApiVault` for native ETH deposits and withdrawals. It
accounts in whole gwei, with maximum amount `2^53 - 1`. The vault pins its
Groth16 proof adapter, state-signing key, clearance-signing key, challenge
period, note lifetime, maximum pause, Poseidon runtime and minimum deposit
(`minDeposit`) as immutable constructor parameters (13 in all). It has no
upgrade path.

This page describes vault revision 4 (`CONCESSION_ESCAPE_VERSION() == 1`,
`LEAF_BOUND_EXIT_VERSION() == 1`), circuit `zkapi-v2-concession-v2`, which
client profiles declare as `vault_revision: 4`, `exit_concession: 1` and
`leaf_bound_exit: 1`. No revision-4 vault is deployed yet, and revision 3
(circuit `zkapi-v2-concession-v1`) is refused by every client. The deployed
vaults run an earlier revision with other rules; see
[Protocol](/docs/protocol#compatibility-and-trust).

The vault stores one word per note, its leaf and status (`noteRecord`).
Exits are bound to that leaf, not to a Merkle root: a withdrawal statement
names the note's leaf and packed fields, and the vault compares the leaf with
the stored one. The request tree (used only by request proofs) is append-only:
deposits append leaves, and only `retireClosedLeaf` zeroes one, a closed
note's. The vault keeps only the tree's frontier and computes `currentRoot()`
on demand; it keeps no root history. Exits, defeats, raises, closes and
expiry claims do no Merkle work.

## Deposit

| Field | Value |
|---|---|
| Method | `deposit(bytes32 commitment, uint128 amount)` (payable, `0x56d2e1ea`) |
| Caller | User's wallet, while not paused |
| Effect | Computes the note leaf, stores it with status `Active` in the note's word, appends it to the request tree's frontier (one compression per trailing one of the note ID, one on average), escrows the native ETH, and emits `NoteDeposited(noteId, commitment, amount, expiryTs)` |
| Reverts | `DepositTooSmall()` below `minDeposit()` (default 1,000,000 gwei), `ZeroAmount()`, `InvalidNativeValue()`, `InvalidCommitment()`, `TreeFull()` at note ID 2^32 − 1 |

Here `commitment` is the Poseidon registration `R` derived from the note
secret, not the anonymous balance commitment signed by the server. The leaf
is one Poseidon permutation `P("zkapi.v2c.leaf", R, F)[1]` of the registration
and the packed fields `F = noteId·2^192 + amount·2^64 + expiryTs`, so it binds
the registration, note ID, amount and expiry. The circuits include this same
leaf in each private balance commitment. A deposit needs no Merkle path, so
deposits never invalidate each other.

Gas depends on the note ID: about 68,000 at an even ID, more where the ID has
trailing ones, and more again the first time a frontier level is written (at
`2^t − 1`; for example 213,318 at note 255 and 243,986 at note 1023; 87,633 on
average over the first 64). An `eth_estimateGas` result covers only the ID it
was estimated at, so the SDK and zkapi-clientd add the extra levels of the
next 64 IDs; a depositor without that policy sends at least 650,000 gas on
mainnet pricing (850,000 where a fresh storage slot costs about 110,000 gas,
as on Sepolia). See
[deposit gas limit](https://github.com/ethereum/zkapi/blob/main/docs/deployment.md#deposit-gas-limit).

The transaction must send exactly `amount * nativeAssetWeiPerUnit` wei;
`nativeAssetWeiPerUnit` is one gwei and `billingToken` is the zero-address
native-asset sentinel. Only deposits carry transaction value. The on-chain
event supplies the actual expiry, rounded up to the vault's one-day expiry
bucket. A wallet that keeps the note's secret, ID, amount and expiry can exit
for good: no path, root or indexer is needed.

## Withdrawal statement

`WithdrawalPublicInputs` contains these 16 fields in order, the Groth16
public-input order (a static tuple, so its ABI words are the public inputs):

```text
protocolVersion, chainId, contractAddress, noteLeaf,
stateSigningKeyX, stateSigningKeyY,
clearanceSigningKeyX, clearanceSigningKeyY,
noteFields, finalBalance, destination, withdrawalNullifier,
kind, nextNullifier, conceded, validUntil
```

`noteLeaf` (word 3) is the note's leaf and `noteFields` (word 8) its packed
fields, `noteId·2^192 + depositAmount·2^64 + expiryTs`. The proof binds the
leaf to the owner's registration and to those fields; the withdrawal circuit
proves no Merkle membership.

`kind` is 0 for an escape, 1 for a mutual close and 2 for an ownership proof,
which only the server accepts: every vault entry point refuses it. The proof
binds `finalBalance + conceded` to the state's balance `B`, and `B` to at most
the deposit. `proof` is the decoded 256-byte Groth16 artifact described in the
[API overview](/docs/api-reference). Every call checks the protocol version,
chain, vault and all four key coordinates (`InvalidDeploymentBinding()`),
refuses a proof after `validUntil` (`ProofExpired()`) and a zero destination or
the vault itself (`InvalidDestination()`). Before the proof it requires
`noteFields < 2^224` (`InvalidNoteFields()`), the note named by
`noteFields >> 192` to be `Active` (`NoteNotActive()`), its stored leaf to
equal `noteLeaf` (`NoteLeafMismatch()`) and the deposit to be at most
`MAX_NATIVE_UNITS` (`InvalidBalance()`); the deposit and expiry it then uses
come from `noteFields`.

Because the deposit comes from the proof-bound fields rather than from
storage, a broken verifier or setup (a forged proof) can pay out the whole
vault in a single forged exit, where a vault that read each deposit from
storage would pay at most that note's deposit per forged exit. The eventual
loss under a broken verifier is total either way (it also forges defeats and
requests). See
[Amendment A3](https://github.com/ethereum/zkapi/blob/main/docs/design/concession-exit.md#amendment-a3-leaf-bound-exits).

## Mutual close

| Field | Value |
|---|---|
| Method | `mutualClose(WithdrawalPublicInputs inputs, bytes proof)` (`0xbce12a6c`) |
| Caller | User's wallet or another transaction submitter, while exits are open |
| Effect | Requires `kind == 1` (else `WrongWithdrawalKind()`), an `Active` note whose stored leaf is `noteLeaf` and `finalBalance` at most the deposit, verifies the proof (whose circuit checks the server's clearance signature), consumes the nullifier, closes the note, and pays the user and the treasury; emits `MutualClose(noteId, nullifier, finalBalance, destination)` |

The user receives `finalBalance` billing units and the treasury
`depositAmount - finalBalance`; the vault multiplies both by
`nativeAssetWeiPerUnit`. A close forwards all gas to the destination, and one
that rejects the payout reverts the close with `NativeTransferFailed()`; the
user can prove the close again to another destination. The close does not
consult `challengedNullifiers`: the operator's clearance is its consent.

## Initiate escape

| Field | Value |
|---|---|
| Method | `initiateEscapeWithdrawal(WithdrawalPublicInputs inputs, bytes proof)` (`0x8cd67c60`) |
| Caller | User's wallet or another transaction submitter, while exits are open |
| Effect | Records an escape that pays `finalBalance` after `challengePeriod` unless defeated, consumes both `withdrawalNullifier` (`N`) and `nextNullifier` (`N⁺`), and emits `EscapeWithdrawalInitiated` then `EscapeConcessionRecorded` |

The checks run in this order: the deployment binding; `kind == 0`
(`WrongWithdrawalKind()`); `validUntil`; the destination; `N⁺` neither zero
nor `N` (`InvalidDeploymentBinding()`); `N` not in `challengedNullifiers`
(`ChallengedNullifier()`); `N⁺` not in `challengedNullifiers`
(`SupersededState()`: the state's successor was already spent); the note
(`InvalidNoteFields()`, `NoteNotActive()`, `NoteLeafMismatch()`, as above) with
`finalBalance + conceded` at most the deposit (`InvalidBalance()`); the proof;
and both
nullifiers unused (`ReplayedNullifier()`, `InvalidFelt()` for a value at or
above the field modulus). The vault then records the escape, which keeps the
deposit and expiry the leaf binds (read through the 6-word `pendingWithdrawals`
and the concession record `pendingConcessions`: `nextNullifier`,
`stateBalance = finalBalance + conceded`, `conceded`), with
`challengeDeadline = now + challengePeriod`. No root is involved, so an
unrelated deposit or retirement cannot invalidate an escape.

## Defeat an escape

| Field | Value |
|---|---|
| Method | `challengeEscapeWithdrawal(uint32 noteId, RequestPublicInputs inputs, bytes proof)` (`0xda0ce43d`) |
| Caller | Anyone, before the deadline, including while paused |
| Effect | Requires a valid request proof whose `requestNullifier` is the escape's `nextNullifier` (else `NotSuccessorEvidence()`), returns the note to `Active`, deletes both records, clears `usedNullifiers` for `N` and `N⁺`, sets `challengedNullifiers[N]`, extends `graceUntil(noteId)` when the note's expiry would otherwise fall within a `challengePeriod` of unpaused time, and emits `EscapeWithdrawalChallenged(noteId, nullifier)` |

A request proof at `N⁺` shows that the owner held and spent the escaped
state's successor, so the escape was from a stale state. A request proof at
the escaped nullifier `N` never defeats. The request's root, time and tag are
not checked: historical evidence is valid. After a defeat, an escape from the
same state reverts `ChallengedNullifier()` and one from the state just below
it `SupersededState()`; older states can escape again and be defeated again.
The note keeps at least one `challengePeriod` of unpaused time before an
expiry claim. The call reverts `NotPendingWithdrawal()` without a pending
escape and `ChallengeExpired()` at or after the deadline.

## Raise a concession

| Field | Value |
|---|---|
| Method | `raiseEscapeConcession(uint32 noteId, RequestPublicInputs inputs, bytes proof, uint128 amount)` (`0xdd0064ba`) |
| Caller | Anyone, before the deadline, including while paused |
| Effect | Requires a valid request proof whose `requestNullifier` is the escaped `N` (else `NotStateEvidence()`), sets `conceded` to `min(amount, inputs.solvencyBound, stateBalance)` and the payout to `stateBalance - conceded`, and emits `EscapeConcessionRaised(noteId, nullifier, conceded, finalBalance)` |

The new concession must exceed the current one (`NotARaise()`), which is
checked before the proof. The deadline and nullifiers do not change, and a
defeat remains possible afterwards. A raise moves value from the payout to the
treasury; it can never take more than the request's own solvency bound.

## Finalize an escape

| Field | Value |
|---|---|
| Method | `finalizeEscapeWithdrawal(uint32 noteId)` (`0xff8f5585`) |
| Caller | Anyone at or after the stored deadline, including while paused |
| Effect | Closes the note, pushes the current `finalBalance` (as raised) to the destination with at most `ESCAPE_PAYOUT_GAS` (100,000) gas, pays the rest of the deposit to the treasury, and emits `EscapeWithdrawalFinalized(noteId, nullifier, finalBalance, destination)` |

If the push fails (the destination rejects ETH or needs more gas), the escape
still closes and the treasury is paid: the balance is added to
`escapePayoutCredits(destination)` (gwei units) and
`EscapePayoutDeferred(noteId, destination, amount)` is emitted just before
`EscapeWithdrawalFinalized`. `EscapeWithdrawalFinalized` alone therefore does
not prove that the destination was paid. Limiting gas cannot force a credit on
a destination that accepts within 100,000 gas and fails only by running out of
gas (the call reverts instead). Both nullifiers stay consumed.

## Claim escape payout

| Field | Value |
|---|---|
| Method | `claimEscapePayout(address destination)` (`0x88c10aee`) |
| Caller | Anyone, including while paused |
| Effect | Pays `destination` all of its credited escape payouts, forwarding all gas, and emits `EscapePayoutClaimed(destination, amount)` |
| Reverts | `ZeroAmount()` (`0x1f2a2005`) when there is no credit; `NativeTransferFailed()` (`0xf4b3b1bc`) while the destination still rejects ETH, and the credit is kept |

Only `destination` is paid, whoever calls. The browser SDK reports an escape
it started whose finalization receipt carries `EscapePayoutDeferred` as
credited, not returned, and offers this claim. See
[Credited escape payouts](https://github.com/ethereum/zkapi/blob/main/sdk/README.md#credited-escape-payouts).

## Claim expired note

| Field | Value |
|---|---|
| Method | `claimExpired(uint32 noteId, bytes32 commitment, uint128 amount, uint64 expiryTs)` (`0xad610550`) |
| Caller | Anyone at or after `effectiveExpiry(noteId, commitment, amount, expiryTs)`, while not paused |
| Effect | Requires an `Active` note (else `NoteNotActive()`) whose stored leaf the arguments reproduce (else `NoteLeafMismatch()`), closes it and pays its full deposit to the treasury; the leaf stays, and the request circuit already refuses requests after the note's expiry. Emits `ExpiredClaimed(noteId, depositAmount)` |

The arguments are the note's `NoteDeposited` values; `expiryTs` is the
nominal expiry the request proof uses. `effectiveExpiry(noteId, commitment,
amount, expiryTs)` adds the paused time since the deposit (pause epochs,
`pausedBefore(noteId)`) and any post-defeat grace (`graceUntil(noteId)`), and
is never earlier than `unpauseClaimGrace` after the latest unpause. Before
then the call reverts `NoteNotExpired()`. A note with a pending escape is not
`Active` and cannot be swept. The view assumes no further pause and returns
zero for an unknown or retired note or a preimage that does not reproduce the
stored leaf.

## Retire a closed leaf

| Field | Value |
|---|---|
| Method | `retireClosedLeaf(uint32 noteId, uint256[32] siblings)` (`0xe41f4c31`) |
| Caller | Anyone, including while paused |
| Effect | For a `Closed` note (else `NoteNotClosed()`), replaces its leaf with zero in the stored word and in the frontier, and emits `ClosedLeafRetired(noteId)` |

Only `siblings[0..ℓ)` are read, where `ℓ = msb(noteId XOR nextNoteId)` is the
level at which the note's path meets the frontier; callers zero-fill the rest,
and at `ℓ = 0` none is read. The sub-path must reproduce the frontier entry of
level `ℓ` (else `StaleRoot()`), which a retirement elsewhere in the same
subtree, a deposit that completes it, or a second call for the same note
changes: refresh the path and retry. This is an operator tool: about 37,700
gas at `ℓ = 0`, 71,960 at level 1, 258,540 at level 8 and 471,788 at level 16.
The challenger calls it after a missed defeat, so that proofs built on later
roots no longer contain the note; the server admits requests at a replaced
root for at most its request-root grace (60 seconds by default).

## Owner controls

| Method | Caller | Effect |
|---|---|---|
| `pause()` | Owner, while not paused, at least `PAUSE_COOLDOWN` (1 day) after the latest unpause (else `PauseCooldown()`) | Blocks `deposit`, `claimExpired`, `setTreasury`, `acceptTreasury`, `withdrawTreasuryArrears` and `renounceOwnership`; blocks `mutualClose` and `initiateEscapeWithdrawal` until `pausedAt() + maxPauseDuration()`; emits `Paused(account)` |
| `unpause()` | Owner, while paused (else `NotPaused()`) | Adds the pause to `totalPausedDuration`, sets `lastUnpausedAt`, and emits `Unpaused(account)` |
| `setTreasury(address)` | Owner, while not paused | Schedules a nonzero `pendingTreasury` other than the vault, ready at `pendingTreasuryReadyAt`; emits `TreasuryChangeScheduled(newTreasury, readyAt)` |
| `acceptTreasury()` | Owner, while not paused | Applies the scheduled treasury once ready; emits `TreasurySet(newTreasury)` |
| `cancelTreasuryChange()` | Owner, at any time | Clears the scheduled change; emits `TreasuryChangeCancelled(cancelledTreasury)` |
| `withdrawTreasuryArrears()` | Anyone, while not paused | Pays `treasuryArrears` to the current treasury; emits `TreasuryArrearsPaid(treasury, amount)` |
| `transferOwnership(address)` | Owner, at any time | Nominates `pendingOwner()` (the zero address cancels); emits `OwnershipTransferStarted(previousOwner, newOwner)`. `owner()` does not change until the nominee accepts |
| `acceptOwnership()` | `pendingOwner()`, at any time | Completes the transfer and clears `pendingOwner()`; emits `OwnershipTransferred(previousOwner, newOwner)`. Any other caller reverts `OwnableUnauthorizedAccount(account)` |
| `renounceOwnership()` | Owner, while not paused | Ownable renunciation; also clears `pendingOwner()` |

A pause blocks new escapes and closes for at most `maxPauseDuration`, which
the constructor requires to be at least twice `challengePeriod`. Defeats,
raises, finalizations, payout claims, leaf retirements, `cancelTreasuryChange`
and ownership transfers stay open while paused, so escapes in flight resolve.
`readyAt` and `pendingTreasuryReadyAt` count on the vault's active clock (wall
clock minus all paused time), so a change waits `treasuryChangeDelay` of
unpaused time. `acceptTreasury()` reverts `NoPendingTreasuryChange()` without
a scheduled change and `TreasuryChangeNotReady()` before it is ready.

Until a nominee accepts with `acceptOwnership()` (`0x79ba5097`), the current
owner keeps every power and can replace the nomination. A rotation away from a
possibly compromised owner key must therefore submit the nomination and the
acceptance consecutively in one private bundle that is included atomically,
never as separate transactions through the public mempool; for a Safe nominee,
the bundle carries a pre-signed Safe `execTransaction` calling
`acceptOwnership()`. See
[owner and operator powers](/docs/protocol#owner-and-operator-powers) and the
[owner key rotation runbook](https://github.com/ethereum/zkapi/blob/main/docs/migration-concession-vault.md#owner-key-rotation).

Treasury payments forward `TREASURY_PAYOUT_GAS` (100,000). A treasury that
reverts or needs more gas does not block the user's payout or an expiry claim:
its share is added to `treasuryArrears` (gwei units) and
`TreasuryPaymentDeferred(treasury, amount)` is emitted. A caller cannot force
that deferral by limiting gas; the whole transaction reverts instead.

## Gas

Measured transaction gas with the development setup (separate cold
transactions, EIP-2929 pricing, `test/GasBaseline.t.sol`): deposit 68,327 at
notes 0 and 2 (87,633 on average over the first 64, at most about 566,000 at

grace); raise 277,437; mutual close 312,073; finalization 56,681; expiry claim
62,361; leaf retirement 37,678 at level 0 to 471,788 at level 16;
`recordRoot` about 465,000 to 543,000. The runtime code is 20,810 bytes.

## Deployment compatibility

The adapter must match circuit `zkapi-v2-concession-v2` and the selected
setup; its `CIRCUIT_ID_HASH` is
`0xcbe7e9ff73a9d6e589b63f04856d01d48cc2306851a024a7621aab30a50488c1`, and it
reports the `IZkApiProofAdapter` interface ID `0x90c99ce1` (ERC-165;
`assertValidWithdrawal` `0xa730baaa`, `verifyWithdrawalOnce` `0x04f7ff68`,
`assertValidRequest` `0x69078eaf`). The
vault's adapter, keys and parameters are immutable. The server, frontend,
deployment manifest and proof assets must match these deployed values, and
clients pin the runtime code hashes of the vault, adapter and Poseidon library
and check them on chain. `Deploy.s.sol` requires an explicit `OWNER`,
`TREASURY`, setup manifest and `MAX_PAUSE_DURATION_SECONDS` outside local
chains, takes `MIN_DEPOSIT` (default 1,000,000 gwei), deploys a single-party setup there only with `ALLOW_DEV_SETUP=1`
(mainnet included), and writes a provisional
manifest that `scripts/expected-codehashes.mjs --finalize` checks on chain
before it records the deployment.
