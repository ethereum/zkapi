---
title: ZkApiVault
description: Native ETH settlement with note-bound Groth16 verification and the concession exit
---

The wallet calls `ZkApiVault` for native ETH deposits and withdrawals. It
accounts in whole gwei, with maximum amount `2^53 - 1`. The vault pins its
Groth16 proof adapter, state-signing key, clearance-signing key, challenge
period, note lifetime and maximum pause as immutable constructor parameters;
its twelfth and last parameter, the activator, is the one address that may
prove activations, which the owner can replace. It has no upgrade path.

This page describes vault revision 4 (`CONCESSION_ESCAPE_VERSION() == 1`,
`NOTE_BOUND_EXIT_VERSION() == 1`), circuit `zkapi-v2-concession-v2`, which
client profiles declare as `vault_revision: 4` and `exit_concession: 1`. No
revision-4 vault is deployed yet. The deployed vaults run an earlier revision
with other rules; see [Protocol](/docs/protocol#compatibility-and-trust).

A deposit only records its note. Every withdrawal is bound to the note as
recorded, so exits, defeats, raises, closes and expiry claims do no Merkle
work and need no root. The vault keeps one tree, the request tree, of which it
stores only the root (`currentRoot`): recorded notes are appended to it in
deposit order by activations, and only `retireClosedLeaf` removes a leaf, a
closed note's. A request proves membership at the current root, so a note can
make anonymous API requests only once it is activated
(`noteId < activationCursor()`).

## Deposit

| Field | Value |
|---|---|
| Method | `deposit(bytes32 commitment, uint128 amount)` (payable, `0x56d2e1ea`) |
| Caller | User's wallet, while not paused |
| Effect | Records the note at `noteId = nextNoteId()` as `notes(noteId)` (`commitment, depositAmount, expiryTs`, status `Active`), escrows the native ETH, and emits `NoteDeposited(noteId, commitment, amount, expiryTs)`; no tree work |
| Reverts | `InvalidNativeValue()` (a value other than `amount` gwei, or `amount` above `MAX_NATIVE_UNITS`), `ZeroAmount()`, `InvalidCommitment()` (zero), `InvalidFelt()` (at or above the field modulus) |

Here `commitment` is the Poseidon registration derived from the note secret,
not the anonymous balance commitment signed by the server. The note's leaf,
`L = Poseidon("zkapi.v2.leaf", noteId, commitment, amount, expiry)`, is fixed
by the record: the circuits include it in each private balance commitment,
and activation appends it to the request tree. The note can exit as soon as
it is recorded; it can make requests once activated.

The transaction must send exactly `amount * nativeAssetWeiPerUnit` wei;
`nativeAssetWeiPerUnit` is one gwei and `billingToken` is the zero-address
native-asset sentinel. Only deposits carry transaction value. The on-chain
event supplies the actual expiry, rounded up to the vault's one-day expiry
bucket. The wallet confirms its note from the receipt's `NoteDeposited` and
`notes(noteId)`; it keeps no path, and deposits never race each other.

## Activate notes

| Field | Value |
|---|---|
| Method | `activateNotes(uint32 firstNoteId, uint256 count, uint256 expectedRoot, uint256 newRoot, bytes proof)` (`0xa2b2c715`) |
| Caller | Only `activator()` (else `NotActivator()`, checked first), while not paused: the operator's activation worker |
| Effect | Verifies an insertion proof of size `count` through the adapter's `assertValidInsertion`, against inputs the vault builds from its own state; sets `currentRoot` to `newRoot`, advances `activationCursor` by `count`, sets `activationFallbackOpensAt` to now + `ACTIVATION_FALLBACK_DELAY`, and emits `NotesActivated(firstNoteId, count, newRoot, true)` |

| Field | Value |
|---|---|
| Method | `activateNotesOnChain(uint32 firstNoteId, uint256 count, uint256[32] siblings)` (`0x027e21e9`) |
| Caller | Anyone, while not paused, from `activationFallbackOpensAt()` on (else `ActivationFallbackClosed()`, checked first); the no-prover fallback |
| Effect | Hashes the batch's leaves, its subtree and the path above it on chain, from `siblings`, the 32 siblings of slot `firstNoteId` at `currentRoot` (entries below the batch's height are ignored); then as above, with `proved = false` and `activationFallbackOpensAt` unchanged |

Both take the next `count` recorded notes, `count` 1, 4 or 16, as one aligned
subtree: `firstNoteId` must be `activationCursor()` (else
`StaleActivation()`), a multiple of `count`, and `firstNoteId + count` at most
`nextNoteId()` (else `InvalidActivation()`, also for another `count`).
`activateNotes` also requires `expectedRoot == currentRoot()`
(`StaleActivation()`, checked before any verification). Its statement is
`[expectedRoot, newRoot, firstNoteId, C_0, M_0, …, C_{count-1}, M_{count-1}]`
with each note's commitment `C_j` and packed amount and expiry
`M_j = depositAmount + expiryTs · 2^128` read from `notes`, so a proof can
neither skip, reorder nor alter a recorded note; a proof that does not verify
reverts `InvalidProof()`. `activateNotesOnChain` reverts `StaleRoot()` when
the siblings do not reproduce `currentRoot`.

The fallback opens `ACTIVATION_FALLBACK_DELAY` (1 hour) after the latest
proved activation, the deployment or the latest unpause, whichever is last,
and stays open until the next proved activation. Batches must be aligned and
the insertion proving keys are public, so while the activator proves nobody
else may activate: a stranger's proved singleton (about 276,000 gas) or
on-chain activation landing just ahead of a batch of 16 would force the other
15 notes through batches of 1 and 4, more than 1.2M gas of extra activations
for the operator. If the activator stops, anyone can activate an hour later.
Exits never depend on activation.

Activation appends each note's original leaf whatever its status: a note that
closed before its activation still gets its leaf, and its status does not
change. An activation or a retirement landing first makes a prepared
activation revert `StaleActivation()` or `StaleRoot()`; deposits landing
meanwhile do not. See the
[activation worker](https://github.com/ethereum/zkapi/blob/main/docs/activation-worker.md)
guide.

## Withdrawal statement

`WithdrawalPublicInputs` contains these 17 fields in order, the Groth16
public-input order (a static tuple, so its ABI words are the public inputs):

```text
protocolVersion, chainId, contractAddress, registrationCommitment,
stateSigningKeyX, stateSigningKeyY,
clearanceSigningKeyX, clearanceSigningKeyY,
noteId, finalBalance, destination, withdrawalNullifier,
kind, nextNullifier, conceded, validUntil, noteMetadata
```

`registrationCommitment` and
`noteMetadata = depositAmount + expiryTs · 2^128` name the note as the vault
records it. Every exit compares them with `notes(noteId)` before it verifies
the proof (`NoteBindingMismatch()`), and the circuit proves that the state's
secret opens `registrationCommitment` and that the state commits to the
note's leaf. An exit therefore needs no root and no Merkle path, and works
whether or not the note is activated; an unrecorded note stores zeros, which
no secret opens.

`kind` is 0 for an escape, 1 for a mutual close and 2 for an ownership proof,
which only the server accepts: every vault entry point refuses it. The proof
binds `finalBalance + conceded` to the state's balance `B`, and `B` to at most
the deposit. `proof` is the decoded 256-byte Groth16 artifact described in the
[API overview](/docs/api-reference); an exit's calldata is 868 bytes. Every
call checks the protocol version, chain, vault and all four key coordinates
(`InvalidDeploymentBinding()`), and refuses a proof after `validUntil`
(`ProofExpired()`), a zero destination or the vault itself
(`InvalidDestination()`) and a note other than the recorded one
(`NoteBindingMismatch()`).

## Mutual close

| Field | Value |
|---|---|
| Method | `mutualClose(WithdrawalPublicInputs inputs, bytes proof)` (`0x5acd3b15`) |
| Caller | User's wallet or another transaction submitter, while exits are open |
| Effect | Requires `kind == 1` (else `WrongWithdrawalKind()`) and the recorded note, verifies the proof (whose circuit checks the server's clearance signature), requires an `Active` note and `finalBalance` at most the deposit, consumes the nullifier, closes the note, and pays the user and the treasury; emits `MutualClose(noteId, nullifier, finalBalance, destination)` |

The user receives `finalBalance` billing units and the treasury
`depositAmount - finalBalance`; the vault multiplies both by
`nativeAssetWeiPerUnit`. A close forwards all gas to the destination, and one
that rejects the payout reverts the close with `NativeTransferFailed()`; the
user can prove the close again to another destination. The close does not
consult `challengedNullifiers`: the operator's clearance is its consent.

## Initiate escape

| Field | Value |
|---|---|
| Method | `initiateEscapeWithdrawal(WithdrawalPublicInputs inputs, bytes proof)` (`0x8e110492`) |
| Caller | User's wallet or another transaction submitter, while exits are open |
| Effect | Records an escape that pays `finalBalance` after `challengePeriod` unless defeated, consumes both `withdrawalNullifier` (`N`) and `nextNullifier` (`N⁺`), and emits `EscapeWithdrawalInitiated` then `EscapeConcessionRecorded` |

The checks run in this order: the deployment binding; `kind == 0`
(`WrongWithdrawalKind()`); `validUntil`; the destination; `N⁺` neither zero
nor `N` (`InvalidDeploymentBinding()`); `N` not in `challengedNullifiers`
(`ChallengedNullifier()`); `N⁺` not in `challengedNullifiers`
(`SupersededState()`: the state's successor was already spent); the note
binding (`NoteBindingMismatch()`); the proof; an `Active` note
(`NoteNotActive()`) with `finalBalance + conceded` at most the deposit
(`InvalidBalance()`); and both nullifiers unused (`ReplayedNullifier()`, `InvalidFelt()` for a value at or
above the field modulus). The vault then stores the pending record
(`pendingWithdrawals`, 5 words) and the concession record
(`pendingConcessions`: `nextNullifier`,
`stateBalance = finalBalance + conceded`, `conceded`), with
`challengeDeadline = now + challengePeriod`. No root is involved, so neither
a deposit nor an activation can invalidate an escape.

## Defeat an escape

| Field | Value |
|---|---|
| Method | `challengeEscapeWithdrawal(uint32 noteId, RequestPublicInputs inputs, bytes proof)` (`0xda0ce43d`) |
| Caller | Anyone, before the deadline, including while paused |
| Effect | Requires a valid request proof whose `requestNullifier` is the escape's `nextNullifier` (else `NotSuccessorEvidence()`), returns the note to `Active`, deletes both records, clears `usedNullifiers` for `N` and `N⁺`, sets `challengedNullifiers[N]`, and emits `EscapeWithdrawalChallenged(noteId, nullifier, currentRoot)` |

A request proof at `N⁺` shows that the owner held and spent the escaped
state's successor, so the escape was from a stale state. A request proof at
the escaped nullifier `N` never defeats. The request's root, time and tag are
not checked: historical evidence is valid. After a defeat, an escape from the
same state reverts `ChallengedNullifier()` and one from the state just below
it `SupersededState()`; older states can escape again and be defeated again.
The note keeps at least one `challengePeriod` of unpaused time before an
expiry claim. The call reverts `NotPendingWithdrawal()` without a pending
escape and `ChallengeExpired()` at or after the deadline.

## Raise a concession

| Field | Value |
|---|---|
| Method | `raiseEscapeConcession(uint32 noteId, RequestPublicInputs inputs, bytes proof, uint128 amount)` (`0xdd0064ba`) |
| Caller | Anyone, before the deadline, including while paused |
| Effect | Requires a valid request proof whose `requestNullifier` is the escaped `N` (else `NotStateEvidence()`), sets `conceded` to `min(amount, inputs.solvencyBound, stateBalance)` and the payout to `stateBalance - conceded`, and emits `EscapeConcessionRaised(noteId, nullifier, conceded, finalBalance)` |

The new concession must exceed the current one (`NotARaise()`), which is
checked before the proof. The deadline and nullifiers do not change, and a
defeat remains possible afterwards. A raise moves value from the payout to the
treasury; it can never take more than the request's own solvency bound.

## Finalize an escape

| Field | Value |
|---|---|
| Method | `finalizeEscapeWithdrawal(uint32 noteId)` (`0xff8f5585`) |
| Caller | Anyone at or after the stored deadline, including while paused |
| Effect | Closes the note, pushes the current `finalBalance` (as raised) to the destination with at most `ESCAPE_PAYOUT_GAS` (100,000) gas, pays the rest of the deposit to the treasury, and emits `EscapeWithdrawalFinalized(noteId, nullifier, finalBalance, destination)` |

If the push fails (the destination rejects ETH or needs more gas), the escape
still closes and the treasury is paid: the balance is added to
`escapePayoutCredits(destination)` (gwei units) and
`EscapePayoutDeferred(noteId, destination, amount)` is emitted just before
`EscapeWithdrawalFinalized`. `EscapeWithdrawalFinalized` alone therefore does
not prove that the destination was paid. Limiting gas cannot force a credit on
a destination that accepts within 100,000 gas and fails only by running out of
gas (the call reverts instead). Both nullifiers stay consumed.

## Claim escape payout

| Field | Value |
|---|---|
| Method | `claimEscapePayout(address destination)` (`0x88c10aee`) |
| Caller | Anyone, including while paused |
| Effect | Pays `destination` all of its credited escape payouts, forwarding all gas, and emits `EscapePayoutClaimed(destination, amount)` |
| Reverts | `ZeroAmount()` (`0x1f2a2005`) when there is no credit; `NativeTransferFailed()` (`0xf4b3b1bc`) while the destination still rejects ETH, and the credit is kept |

Only `destination` is paid, whoever calls. The browser SDK reports an escape
it started whose finalization receipt carries `EscapePayoutDeferred` as
credited, not returned, and offers this claim. See
[Credited escape payouts](https://github.com/ethereum/zkapi/blob/main/sdk/README.md#credited-escape-payouts).

## Claim expired note

| Field | Value |
|---|---|
| Method | `claimExpired(uint32 noteId)` (`0xa940507e`) |
| Caller | Anyone at or after `effectiveExpiry(noteId)`, while not paused |
| Effect | Closes an `Active` note and pays its full deposit to the treasury; its leaf, once activated, stays, and the request circuit already refuses requests after the note's expiry. Emits `ExpiredClaimed(noteId, depositAmount, currentRoot)` |

`notes(noteId)` keeps the nominal `expiryTs` used by the request proof.
`effectiveExpiry(noteId)` adds all paused time since the deposit and any
post-defeat grace, and is never earlier than `unpauseClaimGrace` after the
latest unpause. Before then the call reverts `NoteNotExpired()`. A note with a
pending escape is not `Active` and cannot be swept. The view assumes no
further pause and returns zero for an unknown note.

## Retire a closed leaf

| Field | Value |
|---|---|
| Method | `retireClosedLeaf(uint32 noteId, uint256[32] siblings)` (`0xe41f4c31`) |
| Caller | Anyone, including while paused |
| Effect | For a `Closed` note (else `NoteNotClosed()`) that is activated (else `NoteNotActivated()`), replaces its leaf with zero at the current root, sets the new root, and emits `ClosedLeafRetired(noteId, newRoot)` |

This is an operator tool, and it costs far more gas than an exit: it hashes
the note's path twice on chain. The challenger calls it after a missed
defeat, so that proofs built on later roots no longer contain the note; the
server admits requests only at the current root. A note that closed before
its activation has no leaf yet; activation appends it, and the challenger
retires it then. Stale siblings, including a second call for the same note,
revert `StaleRoot()`: an activation or another retirement changes the root.

## Owner controls

| Method | Caller | Effect |
|---|---|---|
| `pause()` | Owner, while not paused, at least `PAUSE_COOLDOWN` (1 day) after the latest unpause (else `PauseCooldown()`) | Blocks `deposit`, `activateNotes`, `activateNotesOnChain`, `claimExpired`, `setTreasury`, `acceptTreasury`, `withdrawTreasuryArrears` and `renounceOwnership`; blocks `mutualClose` and `initiateEscapeWithdrawal` until `pausedAt() + maxPauseDuration()`; emits `Paused(account)` |
| `unpause()` | Owner, while paused (else `NotPaused()`) | Adds the pause to `totalPausedDuration`, sets `lastUnpausedAt`, sets `activationFallbackOpensAt` to now + `ACTIVATION_FALLBACK_DELAY` (the activator gets the full delay before anyone else may activate), and emits `Unpaused(account)` |
| `setActivator(address)` | Owner, at any time | Replaces `activator()` with a nonzero address (else `Unauthorized()`), leaving `activationFallbackOpensAt` alone; emits `ActivatorChanged(previousActivator, newActivator)` |
| `setTreasury(address)` | Owner, while not paused | Schedules a nonzero `pendingTreasury` other than the vault, ready at `pendingTreasuryReadyAt`; emits `TreasuryChangeScheduled(newTreasury, readyAt)` |
| `acceptTreasury()` | Owner, while not paused | Applies the scheduled treasury once ready; emits `TreasurySet(newTreasury)` |
| `cancelTreasuryChange()` | Owner, at any time | Clears the scheduled change; emits `TreasuryChangeCancelled(cancelledTreasury)` |
| `withdrawTreasuryArrears()` | Anyone, while not paused | Pays `treasuryArrears` to the current treasury; emits `TreasuryArrearsPaid(treasury, amount)` |
| `transferOwnership(address)` | Owner, at any time | Nominates `pendingOwner()` (the zero address cancels); emits `OwnershipTransferStarted(previousOwner, newOwner)`. `owner()` does not change until the nominee accepts |
| `acceptOwnership()` | `pendingOwner()`, at any time | Completes the transfer and clears `pendingOwner()`; emits `OwnershipTransferred(previousOwner, newOwner)`. Any other caller reverts `OwnableUnauthorizedAccount(account)` |
| `renounceOwnership()` | Owner, while not paused | Ownable renunciation; also clears `pendingOwner()` |

A pause blocks new escapes and closes for at most `maxPauseDuration`, which
the constructor requires to be at least twice `challengePeriod`. Defeats,
raises, finalizations, payout claims, leaf retirements, `cancelTreasuryChange`,
`setActivator` and ownership transfers stay open while paused, so escapes in
flight resolve and a lost or compromised activation key can be replaced at
once.
`readyAt` and `pendingTreasuryReadyAt` count on the vault's active clock (wall
clock minus all paused time), so a change waits `treasuryChangeDelay` of
unpaused time. `acceptTreasury()` reverts `NoPendingTreasuryChange()` without
a scheduled change and `TreasuryChangeNotReady()` before it is ready.

Until a nominee accepts with `acceptOwnership()` (`0x79ba5097`), the current
owner keeps every power and can replace the nomination. A rotation away from a
possibly compromised owner key must therefore submit the nomination and the
acceptance consecutively in one private bundle that is included atomically,
never as separate transactions through the public mempool; for a Safe nominee,
the bundle carries a pre-signed Safe `execTransaction` calling
`acceptOwnership()`. See
[owner and operator powers](/docs/protocol#owner-and-operator-powers) and the
[owner key rotation runbook](https://github.com/ethereum/zkapi/blob/main/docs/migration-concession-vault.md#owner-key-rotation).

Treasury payments forward `TREASURY_PAYOUT_GAS` (100,000). A treasury that
reverts or needs more gas does not block the user's payout or an expiry claim:
its share is added to `treasuryArrears` (gwei units) and
`TreasuryPaymentDeferred(treasury, amount)` is emitted. A caller cannot force
that deferral by limiting gas; the whole transaction reverts instead.

## Gas

Measured transaction gas (21,000, calldata and execution, with cold
contracts) with the development setup and the CI-pinned Forge: escape
481,776; defeat 357,418; raise 320,016; mutual close 395,657; finalization
80,500; expiry claim 72,835; `activateNotes` 275,635 for 1 note, 337,933 for
4 and 594,662 for 16 (about 37,200 per note), its write of
`activationFallbackOpensAt` included; `activateNotesOnChain` 1,656,574 for 1
note, 1,890,663 for 4 and 3,077,148 for 16. A deposit costs about 77,200 gas
on Anvil once the vault holds notes. The runtime code is 20,940 bytes.

## Deployment compatibility

The adapter must match circuit `zkapi-v2-concession-v2` and the selected
setup, with all five verifying keys (request, withdrawal and the 1-, 4- and
16-note insertions); its `CIRCUIT_ID_HASH` is
`0xcbe7e9ff73a9d6e589b63f04856d01d48cc2306851a024a7621aab30a50488c1`. The
vault's adapter, keys and parameters are immutable. The server, frontend,
deployment manifest and proof assets must match these deployed values, and
clients pin the runtime code hashes of the vault, adapter and Poseidon library
and check them on chain. `Deploy.s.sol` requires an explicit `OWNER`,
`TREASURY`, `ACTIVATOR` (the activation worker's sender), setup manifest and
`MAX_PAUSE_DURATION_SECONDS` outside local chains, deploys a single-party
setup there only with `ALLOW_DEV_SETUP=1` (mainnet included), and writes a
provisional manifest that `scripts/expected-codehashes.mjs --finalize`
checks on chain before it records the deployment.
