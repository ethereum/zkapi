---
title: indexer
description: Contract-event mirror and depth-32 Merkle paths
---

The indexer applies native vault events to a local Merkle tree. The browser
uses it for deposits and, when it has no deposit-time path, for proving; the
server uses it to confirm the current root and to learn which nullifiers are
public; the challenge service uses it for a leaf retirement's path and as a
hint of pending escapes. Defeats and raises need no indexer.

| Method and path | Result |
| --- | --- |
| `GET /health` | Sync status and detail (internal) |
| `GET /metrics` | Prometheus text metrics (internal) |
| `GET /v1/tree/root` | `{ root, next_note_id, block_number, block_hash }` |
| `GET /v1/tree/next-note-id` | `{ next_note_id, root, block_number, block_hash }` |
| `GET /v1/tree/snapshot` | `{ root, next_note_id, leaves, block_number, block_hash }` |
| `GET /v1/tree/notes/{note_id}/path` | Occupied leaf, 32 siblings, `root`, `block_number`, `block_hash` |
| `GET /v1/tree/notes/{note_id}/zero-path` | Empty-slot path for a deposit, with the same fields; deprecated (`Deprecation: true`) |
| `GET /v1/tree/roots/{root}` | `{ root, known, current_root, block_number, block_hash }`: whether the vault ever set `root` |
| `GET /v1/nullifiers/{nullifier}/published` | `{ nullifier, published, block_number, block_hash }`: whether a vault event named it as an exit's nullifier or successor nullifier |
| `GET /v1/escapes/pending` | Pending escape withdrawals in the served view, with their concessions (internal) |

The root, leaf, and siblings use canonical BN254 field encodings; a path
parameter that is not one answers `400 invalid_request`. The indexer decodes
`NoteDeposited`, `MutualClose`, `EscapeWithdrawalInitiated`,
`EscapeConcessionRecorded`, `EscapeConcessionRaised`,
`EscapeWithdrawalChallenged`, `EscapeWithdrawalFinalized`, `ExpiredClaimed`
and `ClosedLeafRetired` strictly from Ethereum JSON-RPC and ignores other
vault events. The tree is append-only: only `NoteDeposited` sets a leaf and
only `ClosedLeafRetired` zeroes one, and every other event's root must equal
the computed root. The indexer also keeps every root the vault ever set (the
vault accepts withdrawal proofs at any of them) and every nullifier a vault
event published. The block fields name the block whose vault state the
response describes; a path's siblings hash to its `root`.

An indexer cannot forge membership: clients and contracts recompute roots from
the supplied paths. Incorrect or stale paths can cause proving or transaction
failure. The deployment pins the vault and network independently of indexer
responses.

## Verified views

Every tree response comes from one verified view: the chain head, or the
newest recent block whose vault state the indexer could confirm. The indexer
applies each batch of events with consistency checks, then reads the vault's
`currentRoot()` and `nextNoteId()` at that block hash and publishes the view
only when both match its mirror. It persists a checkpoint only at
`--confirmations` blocks behind the head (default 12), and re-derives the head
view from that checkpoint on every new head, so a shallower reorganization is
absorbed. A checkpoint restored at startup is served only once this process
has verified it, or a view built on it, against the vault. A deeper
reorganization that changed the vault state, or a mirror that keeps
disagreeing with the vault, takes the tree routes out of service and rebuilds
the mirror from the deployment block. Automatic rebuilds are rate-limited.

A shallow reorganization can also orphan the block of the view being served.
The indexer keeps serving that view, with `/health` `ok`, until it publishes a
new one: while its RPC cannot verify the new head, for up to
`--stale-after-secs` (120 s) before it reports `stale`; while the re-derived
view disagrees with the vault, until it declares the mirror diverged, after
three polls and at least 30 seconds. A deposit built from such a view reverts
`StaleRoot()`, and a withdrawal at a root the vault never held
`UnknownRoot()`; build them again from a fresh path. The challenger checks a
retirement's path against the vault's live root and is not misled.

While no verified view is available, every tree route,
`/v1/nullifiers/{nullifier}/published` and `/v1/escapes/pending` return `503`
with `Retry-After: 5` and the same public body:

```json
{"status":"unavailable","error_code":"indexer_unavailable","error_message":"the indexer has no verified view of the vault state; retry later","retriable":true,"retry_after_seconds":5}
```

Retry after the indicated delay; never build a transaction from an unverified
tree. The public body never reveals the indexer's internal state.
`GET /health` returns `200` only with status `ok`; otherwise it returns `503`
with status `syncing`, `stale`, `diverged`, or `rebuilding`. Its body reports
the head, served and confirmed blocks, roots, lag, failures, divergence and
rebuild counts, `known_root_count`, `published_nullifier_count`, and
`missed_re_escape_count` with its subsets `missed_re_escape_finalized_count`
and `missed_re_escape_raised_count`, exported as
`zkapi_indexer_missed_re_escapes_total{event="challenged"}`,
`{event="finalized"}` and `{event="raised"}` on `/metrics`. These count
committed defeats, raises and finalizations of an escape the indexer never saw
initiated, once per escape: its RPC's logs missed an escape of the note, or a
reorganization below the checkpoint replaced it. The indexer applies such an
event and keeps serving. Each is logged once, a defeat or a raise at WARN and
a finalization at ERROR. The counts restart with the process. The view becomes
`stale` after `--stale-after-secs` (default 120) without a verified poll, or
when the RPC's head block is older than `--max-head-age-secs` (default 180;
`0` disables the check for chains that mine on demand). Keep `/health`,
`/metrics`, `/v1/nullifiers/` and `/v1/escapes/pending` internal; the
reference gateway proxies only `/v1/tree/` to the indexer.

`GET /v1/escapes/pending` returns
`{ block_number, block_hash, root, escapes: [{ note_id, withdrawal_nullifier, challenge_deadline, final_balance, next_nullifier, state_balance, conceded }] }`
from the same verified view. Escapes change no leaf, so the root check does
not cover the list at all: each entry is the last one the indexer applied from
the vault's logs, and is a hint. Logs that miss an escape, its defeat or its
finalization leave the list wrong until a later event of the note or a resync.
Read `pendingWithdrawals(noteId)` and `pendingConcessions(noteId)` from the
vault before acting on an entry. The challenge service tracks escapes from its
own event scan and the vault, and uses the list only to find escapes its scan
missed.

Both `zkapi-indexerd` and `zkapi indexer` accept `--confirmations`,
`--chain-id`, `--resync`, `--stale-after-secs`, `--max-block-range` (default
1000, above `--confirmations`) and `--max-head-age-secs`. `--resync`, or a
`<cursor>.resync` file, archives the checkpoint and replays from
`--from-block`. A checkpoint (version 3) is bound to one chain, vault and
circuit, and records the last block with a lifecycle event, so a deep
reorganization near one rebuilds the mirror. A version-2 checkpoint, whose
tree removed leaves on exits, is archived and replayed. At startup the
indexer requires the vault's `CONCESSION_ESCAPE_VERSION()` to be 1. The RPC must
support `eth_getBlockByHash`, `eth_getLogs` results with block hashes and log
indexes, and EIP-1898 `eth_call` by `{ blockHash, requireCanonical: true }`
with state for at least the confirmation depth; archive state is not required.

## Leaf binding and private path lookup

The tree uses Poseidon over the BN254 scalar field with 32 sibling levels.
Each occupied leaf binds the note ID, secret-derived registration, deposit,
and expiry. The note-bound request and withdrawal circuits use this exact
leaf in both membership verification and the signed balance commitment.
The indexer's `/v1` URLs are independent of the proof protocol's v2 version.

`GET /v1/tree/snapshot` returns the whole tree's leaves for the served view.
Clients can rebuild the tree and derive paths locally without revealing a
particular note ID in a request URL. Every client receives the same snapshot
for the same view.

Use current-root sibling paths when submitting a deposit or a leaf
retirement. A withdrawal proof may use any root the vault ever held, including
the one of the wallet's deposit-time path, and needs no siblings at
submission. A defeat or raise supplies the original request proof with its
historical root; do not rewrite its public inputs to the indexer's latest
root.
