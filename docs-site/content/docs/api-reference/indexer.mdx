---
title: indexer
description: Contract-event mirror of the recorded notes and the request tree's depth-32 paths
---

The indexer applies native vault events to a local mirror of the recorded
notes and of the request tree. The browser uses it for request paths (exits
need none); the server uses it to confirm the current root and to learn which
nullifiers are public; the activation worker uses it for the siblings of the
activation cursor's slot; the challenge service uses it for a leaf
retirement's path and as a hint of pending escapes. Exits, defeats and raises
need no indexer.

| Method and path | Result |
| --- | --- |
| `GET /health` | Sync status and detail (internal) |
| `GET /metrics` | Prometheus text metrics (internal) |
| `GET /v1/tree/root` | `{ root, next_note_id, activation_cursor, block_number, block_hash }` |
| `GET /v1/tree/next-note-id` | `{ next_note_id, root, block_number, block_hash }` |
| `GET /v1/tree/snapshot` | `{ root, next_note_id, activation_cursor, leaves, note_leaves, notes, block_number, block_hash }`; `?parts=tree` the header and `leaves` only, `?parts=records` the header, `note_leaves` and `notes` only |
| `GET /v1/tree/notes/{note_id}/path` | `{ note_id, leaf, siblings, root, activated, activation_cursor, block_number, block_hash }`: slot `note_id`'s tree leaf (0 when not activated) and its 32 siblings in the current tree |
| `GET /v1/nullifiers/{nullifier}/published` | `{ nullifier, published, block_number, block_hash }`: whether a vault event named it as an exit's nullifier or successor nullifier |
| `GET /v1/escapes/pending` | Pending escape withdrawals in the served view, with their concessions (internal) |

The root, leaves, commitments and siblings use canonical BN254 field
encodings; a path parameter that is not one answers `400 invalid_request`.
The indexer decodes `NoteDeposited`, `NotesActivated`, `MutualClose`,
`EscapeWithdrawalInitiated`, `EscapeConcessionRecorded`,
`EscapeConcessionRaised`, `EscapeWithdrawalChallenged`,
`EscapeWithdrawalFinalized`, `ExpiredClaimed` and `ClosedLeafRetired`
strictly from Ethereum JSON-RPC and ignores other vault events.
`NoteDeposited` records a note (`note_id, commitment, amount, expiry_ts`) and
does not touch the tree. `NotesActivated(firstNoteId, count, newRoot)` must
start at the mirror's activation cursor, with `count` 1, 4 or 16, aligned and
within the recorded notes; it appends those notes' recorded leaves and its
`newRoot` must equal the computed root. `ClosedLeafRetired` zeroes an
activated, closed note's leaf, with the same root check. The tree is
append-only otherwise: exits change no leaf. The indexer also keeps every
nullifier a vault event published. The block fields name the block whose
vault state the response describes; a path's siblings hash to its `root`.

An indexer cannot forge membership: clients and contracts recompute roots from
the supplied paths. Incorrect or stale paths can cause proving or transaction
failure. The deployment pins the vault and network independently of indexer
responses.

## Verified views

Every tree response comes from one verified view: the chain head, or the
newest recent block whose vault state the indexer could confirm. The indexer
applies each batch of events with consistency checks, then reads the vault's
`currentRoot()`, `nextNoteId()` and `activationCursor()` at that block hash
and publishes the view only when all three match its mirror. That check
covers the tree and the number of recorded notes. The records above the
activation cursor, note statuses, open escapes and published nullifiers come
from the same logs but change no root (a pending record is checked when its
activation's root is), so they are hints: read `notes(noteId)` and the other
getters from the vault before acting on them. It persists a checkpoint only at
`--confirmations` blocks behind the head (default 12), and re-derives the head
view from that checkpoint on every new head, so a shallower reorganization is
absorbed. A checkpoint restored at startup is served only once this process
has verified it, or a view built on it, against the vault. A deeper
reorganization that changed the vault state, or a mirror that keeps
disagreeing with the vault, takes the tree routes out of service and rebuilds
the mirror from the deployment block. Automatic rebuilds are rate-limited.

A shallow reorganization can also orphan the block of the view being served.
The indexer keeps serving that view, with `/health` `ok`, until it publishes a
new one: while its RPC cannot verify the new head, for up to
`--stale-after-secs` (120 s) before it reports `stale`; while the re-derived
view disagrees with the vault, until it declares the mirror diverged, after
three polls and at least 30 seconds. An on-chain activation or a retirement
built from such a view reverts `StaleRoot()`, and a request proof at a root
that is no longer current is refused by the server; build them again from a
fresh path. Deposits and exits need no path. The activation worker and the
challenger check a path against the vault's live root and are not misled.

While no verified view is available, every tree route,
`/v1/nullifiers/{nullifier}/published` and `/v1/escapes/pending` return `503`
with `Retry-After: 5` and the same public body:

```json
{"status":"unavailable","error_code":"indexer_unavailable","error_message":"the indexer has no verified view of the vault state; retry later","retriable":true,"retry_after_seconds":5}
```

Retry after the indicated delay; never build a transaction from an unverified
tree. The public body never reveals the indexer's internal state.
`GET /health` returns `200` only with status `ok`; otherwise it returns `503`
with status `syncing`, `stale`, `diverged`, or `rebuilding`. Its body reports
the head, served and confirmed blocks, roots, next note IDs and activation
cursors (`activation_cursor`, `confirmed_activation_cursor`), lag, failures,
divergence and rebuild counts, `published_nullifier_count`, and
`missed_re_escape_count` with its subsets `missed_re_escape_finalized_count`
and `missed_re_escape_raised_count`, exported as
`zkapi_indexer_missed_re_escapes_total{event="challenged"}`,
`{event="finalized"}` and `{event="raised"}` on `/metrics`. These count
committed defeats, raises and finalizations of an escape the indexer never saw
initiated, once per escape: its RPC's logs missed an escape of the note, or a
reorganization below the checkpoint replaced it. The indexer applies such an
event and keeps serving. Each is logged once, a defeat or a raise at WARN and
a finalization at ERROR. The counts restart with the process. The view becomes
`stale` after `--stale-after-secs` (default 120) without a verified poll, or
when the RPC's head block is older than `--max-head-age-secs` (default 180;
`0` disables the check for chains that mine on demand). Keep `/health`,
`/metrics`, `/v1/nullifiers/` and `/v1/escapes/pending` internal; the
reference gateway proxies only `/v1/tree/` to the indexer.

`GET /v1/escapes/pending` returns
`{ block_number, block_hash, root, escapes: [{ note_id, withdrawal_nullifier, challenge_deadline, final_balance, next_nullifier, state_balance, conceded }] }`
from the same verified view. Escapes change no leaf, so the root check does
not cover the list at all: each entry is the last one the indexer applied from
the vault's logs, and is a hint. Logs that miss an escape, its defeat or its
finalization leave the list wrong until a later event of the note or a resync.
Read `pendingWithdrawals(noteId)` and `pendingConcessions(noteId)` from the
vault before acting on an entry. The challenge service tracks escapes from its
own event scan and the vault, and uses the list only to find escapes its scan
missed.

Both `zkapi-indexerd` and `zkapi indexer` accept `--confirmations`,
`--chain-id`, `--resync`, `--stale-after-secs`, `--max-block-range` (default
1000, above `--confirmations`) and `--max-head-age-secs`. `--resync`, or a
`<cursor>.resync` file, archives the checkpoint and replays from
`--from-block`. A checkpoint (version 4) is bound to one chain, vault and
circuit (`zkapi-v2-concession-v2`), and records the last block with a
lifecycle event (deposits included), so a deep reorganization near one
rebuilds the mirror. An earlier checkpoint (version 3, whose deposits
inserted leaves, or version 2, whose exits removed them) is archived and
replayed; one of another circuit stops the indexer until `--resync`. At
startup the indexer requires the vault's `CONCESSION_ESCAPE_VERSION()` and
`NOTE_BOUND_EXIT_VERSION()` to be 1. The RPC must
support `eth_getBlockByHash`, `eth_getLogs` results with block hashes and log
indexes, and EIP-1898 `eth_call` by `{ blockHash, requireCanonical: true }`
with state for at least the confirmation depth; archive state is not required.

## Leaf binding and private path lookup

The tree uses Poseidon over the BN254 scalar field with 32 sibling levels.
Each leaf binds the note ID, secret-derived registration, deposit and expiry,
as the vault recorded them. The request circuit proves membership of this
exact leaf and binds it into the signed balance commitment; the withdrawal
circuit binds the same leaf into the commitment, but proves no membership.
The indexer's `/v1` URLs are independent of the proof protocol's v2 version.

`GET /v1/tree/snapshot` returns, for the served view, `leaves`: the tree
leaves of note IDs `0 .. next_note_id - 1`, exactly the leaves under `root`
(0 for a note not activated yet and for a retired one); `note_leaves`: the
recorded leaf of every recorded note, activated or not; and `notes`: the
records `{ note_id, commitment, amount, expiry_ts }`. Clients rebuild the tree
and derive paths locally without revealing a particular note ID in a request
URL, and corroborate a deposit against its recorded leaf. Every client
receives the same snapshot, or the same part of it, for the same view.

The optional query parameter `parts` returns a part of the snapshot:

| `parts` | Fields |
| --- | --- |
| absent | the header (`root`, `next_note_id`, `activation_cursor`, `block_number`, `block_hash`), `leaves`, `note_leaves` and `notes` |
| `tree` | the header and `leaves` |
| `records` | the header, `note_leaves` and `notes` |

A part leaves the other fields out of the body, and its header describes the
same verified view as its arrays. Which part a client asks for depends on its
role, never on a note: the browser SDK asks for `parts=tree` to build a
request path, zkapi-clientd for `parts=records` to corroborate a deposit, and
each also accepts the full snapshot from an older indexer that ignores
`parts`. Any other value, or `parts` given twice, answers `400` with
`{"status":"error","error_code":"invalid_request","error_message":"parts must be tree or records","retriable":false}`;
other query parameters are ignored.

A path is valid for any slot: the slot's tree leaf (the note's leaf once it
is activated, 0 before that and after a retirement) and its siblings. At the
activation cursor that is the empty slot's path, which the activation worker
and `activateNotesOnChain` need. Use current-root paths for a request, an activation or a leaf
retirement. Withdrawals need no path at all. A defeat or raise supplies the
original request proof with its historical root; do not rewrite its public
inputs to the indexer's latest root.
